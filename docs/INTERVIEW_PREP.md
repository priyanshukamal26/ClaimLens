# INTERVIEW_PREP.md — Hackathon Judge Q&A & Demo Flow

This document prepares you for presenting ClaimLens Nexus to hackathon judges. It covers the optimal demo flow and answers to likely technical questions.

## The Demo Flow (3-4 Minutes)

**1. The Hook (30 seconds)**
- Open on the **Landing Page**. "Insurance fraud costs billions, but existing detection systems are rigid rule engines that flag too much or too little. Meet ClaimLens Nexus."
- Click "Enter Application".

**2. Executive Overview (45 seconds)**
- Show the **Executive Overview**. Point out the KPI band and the dual charts.
- Scroll down to the **Regulatory Context Panel**. Explain: "We aren't building in a vacuum. We ingest real IRDAI and PMFBY data so decision-makers have regulatory baselines right next to their operational data."

**3. The Review Queue & Decision Log (60 seconds)**
- Go to **Review Queue**. This is where the magic happens.
- Click the top claim. Explain the **3-Layer Anomaly Detection**:
  - Layer 1: Rules Engine (Domain logic)
  - Layer 2: Isolation Forest (Statistical outliers)
  - Layer 3: Graph Community (Network collusion)
- Click "Investigate" and show the green toast notification.
- Immediately switch to **Decision Log**. Show that the decision appears instantly. Mention the architectural choice: "Analytics runs on DuckDB for speed, but operational decisions write to SQLite for immediate consistency and auditability. Insight ≠ Decision."

**4. Ask ClaimLens & Security (45 seconds)**
- Go to **Ask ClaimLens**.
- Click one of the Golden Queries (e.g., "Which hospitals have the highest anomaly rates?").
- While it types, explain: "This is a Natural Language to SQL engine. But we built it securely. The LLM's SQL is parsed into an Abstract Syntax Tree by `sqlglot` and checked against a strict allowlist. It physically cannot drop tables or exfiltrate data."

**5. The Morning Brief (15 seconds)**
- Finish on the **Morning Brief**. "An AI-synthesized daily summary so investigators know exactly where to start their day."

## Anticipated Judge Questions & Answers

### Q: "How are you handling hallucinations when the LLM generates SQL?"
**A:** "We don't trust the LLM. The LLM generates SQL, but before execution, it is parsed by `sqlglot` into an Abstract Syntax Tree (AST). We have a strict allowlist validator that ensures the query is a `SELECT` statement, only touches our 6 allowed tables, and doesn't use any dangerous functions. If it fails, the query is blocked. We have a 25-case hostile test suite proving this."

### Q: "What if the LLM provider goes down during a critical investigation?"
**A:** "We built a 4-stage fallback chain. If Groq (our primary) hits a rate limit or fails, we automatically failover to Gemini. If Gemini fails, we check a local semantic cache for similar past queries. If that fails, we fall back to parameterized templates. The system never goes down."

### Q: "Why DuckDB *and* SQLite? Isn't one enough?"
**A:** "They serve two conflicting needs. DuckDB is incredibly fast for the complex analytical queries generated by the LLM, but it's designed for OLAP, not concurrent transactional writes. SQLite is our operational OLTP store. Human decisions are written instantly to SQLite, ensuring the audit trail is never locked, while DuckDB handles the heavy reading."

### Q: "How does your anomaly detection work? Is it just rules?"
**A:** "No, it's a 3-layer ensemble. Layer 1 is deterministic rules (e.g., claims > premium). Layer 2 is an Isolation Forest model to catch multi-dimensional statistical outliers that rules miss. Layer 3 is a Graph/Louvain community detection algorithm to catch organized fraud rings sharing the same hospitals and agents."

### Q: "Where is the data from?"
**A:** "The operational data (policies, claims, hospitals) is generated by a synthetic data engine we built, calibrated to match real-world distributions. The regulatory context data (IRDAI incurred claims ratios, PMFBY crop data) is real, fetched via API from government sources to provide grounding."

### Q: "Is this production ready?"
**A:** "The architecture is designed for production. The read-only DuckDB analytics layer prevents SQL injection via AST parsing, we have a CI/CD pipeline running security tests on every commit, and the UX handles loading and error states gracefully."
